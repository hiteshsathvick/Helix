# ADR 0003: Cloud deployment target and Phase 22 scope

## Context

Phase 22 (SPEC.md §33 CI/CD, §36 Production Deployment) asks for: on merge to main, build/push an image, run migrations against staging, and deploy to staging automatically; production deploy is a separate gated manual approval. The infra layer needs a concrete container platform ("Fly.io/Render early...") plus managed Postgres, managed Redis, and S3-compatible storage, described via Terraform.

Every previous phase in this project has been free to build and verify end-to-end locally. This one is different: a *real* staging/prod environment requires an actual cloud account and real recurring cost (a managed Postgres/Redis instance and compute don't have a meaningful free tier once left running). Asked directly, the choice made for this phase was: **build the pipeline and IaC as complete, real code — but do not create any cloud account, run `terraform apply`, or spend any money.** That constrains what "shipped" means here (see Consequences).

Writing real, specific Terraform requires picking an actual target rather than something generic, so this ADR also records that choice.

## Decision

- **Render** for compute (api, worker, frontend) plus managed Postgres and managed Redis (Render's "Key Value"). Render's own Terraform provider (`render-oss/render`) covers all of these from one account/provider block, which is why it wins over the other SPEC-named option, Fly.io: Fly's Terraform support doesn't cover managed Postgres/Redis as cleanly, so choosing it would mean bolting on a separate provider or manual setup for the data stores anyway.
- **AWS S3** for object storage — Render has no native S3-equivalent. The app's storage layer (`backend/app/core/storage.py`) is already a plain boto3/S3-endpoint client (this is exactly why MinIO works as the local/dev S3 stand-in), so pointing it at real S3 in staging/prod needs zero application code changes, only different `S3_*` env vars (`infra/terraform/main.tf`'s `local.backend_env_vars`).
- **GitHub Container Registry (ghcr.io)** for images — free, uses the repo's own built-in `GITHUB_TOKEN`, no new account or secret needed. This is the one piece of this phase that runs for real, not just "ready to run": `.github/workflows/deploy.yml`'s `build-and-push` job has no missing-secret gate and will push real images to this repo's Packages tab on every merge to main from here on.
- Deploy steps that need real credentials (`STAGING_MIGRATIONS_DATABASE_URL`, `RENDER_*_DEPLOY_HOOK`, `PROD_MIGRATIONS_DATABASE_URL`) are gated with step-level `if: secrets.X != ''` checks rather than left unwritten — the workflow fires on every merge (satisfying "deploy to staging automatically" literally) and reports a clean skip, not a red X, until those secrets exist.
- Production deploy's manual-approval gate uses a GitHub **Environment** named `production` with required reviewers, rather than custom approval scripting — this is a native GitHub feature built exactly for "one gated click."
- Branch protection ("green CI + review required" on main) is a repo-wide setting, not something expressible in a workflow file, and changing it is a standing-configuration change outside what I do without your explicit go-ahead. Once you're ready: `gh api repos/<owner>/helix/branches/main/protection --method PUT --input <config>`, or Settings → Branches → add rule for `main` requiring the `lint`, `type-check`, `test`, `frontend-test`, and `build` checks from `ci.yml`, plus at least one approving review.

## Consequences

- **Real today**: `infra/terraform/` is complete, `terraform fmt`/`validate`-clean Terraform for this exact shape (Render web services + background worker + Postgres + Key Value, an S3 bucket + scoped IAM user per environment). `.github/workflows/deploy.yml` is a complete, real pipeline. `build-and-push` will actually run and produce real ghcr.io images the moment this lands on main.
- **Needs a real account to go live**: nothing here has been `terraform apply`'d — no Render account, no AWS account, no money spent. To actually stand up staging: create the accounts, run `terraform apply -var-file=staging.tfvars` (supplying `-var backend_image=... -var frontend_image=... -var jwt_signing_keys_json=... -var connector_encryption_key=...` from real values, plus `RENDER_API_KEY`/AWS credentials as provider env vars), then add these repo secrets so `deploy.yml`'s gated steps stop skipping: `STAGING_MIGRATIONS_DATABASE_URL`, `RENDER_STAGING_API_DEPLOY_HOOK`, `RENDER_STAGING_WORKER_DEPLOY_HOOK`, `RENDER_STAGING_FRONTEND_DEPLOY_HOOK`, and the `PROD_*`/`RENDER_PROD_*` equivalents for production plus a required reviewer on the `production` Environment.
- Terraform state is local (gitignored), not remote — fine for a single operator applying by hand, not fine once CI or a second person needs to run `apply`. `main.tf`'s header comment documents the S3-backend chicken-and-egg problem and the two real options (a manually-bootstrapped state bucket, or Terraform Cloud's free tier) as the next step whenever a real `apply` is imminent, deliberately not solved speculatively now.
- If Render turns out to be the wrong long-term fit, only `infra/terraform/` changes — the backend/frontend code has no Render-specific assumptions (env vars and a plain Dockerfile are the entire interface).
